# NC-Baseball-alert

NC 다이노스 경기의 **시작 · 취소 · 득점 · 종료**를 그 시점에 푸시로 알려주고,
일자별 기록과 포스트시즌 진출 상황을 앱에서 볼 수 있는 PWA입니다.

- 홈 화면에 추가하면 아이콘 · 전체화면 · 푸시까지 네이티브 앱처럼 동작 (Android / iOS 16.4+)
- **기록 · 일정 · 순위 · 알림** 네 화면
- 일정 탭은 **시즌 전체**를 월별로 보여주고, 홈경기를 강조하며 지난 경기에는 결과를 붙임.
  **리스트 ↔ 달력** 전환과 **오늘** 버튼(현재 보는 뷰에서 오늘 위치로 이동) 제공
- 기록 탭은 각 경기의 **실제 시작·종료 시각**, **이닝별 전광판**, 이벤트 타임라인을 함께 표시
- 일정 탭은 화면 상단(제목·탭·홈/원정/오늘/리스트·달력 전환·요약줄)이 고정되고 카드만 스크롤됨
- 알림 종류(4가지), 시리즈 범위(정규시즌 / 포스트시즌), **홈경기만 받기**를 각각 켜고 끌 수 있음
- 알림 종류별 **진동 패턴**이 다르고, 종류별로 진동만 따로 끌 수 있음(기기에 저장)
- 알림이 단말에 안 뜨면 **5분 뒤 한 번 다시 보냄** (아래 "알림 배달 보장")
- 포스트시즌 경기는 알림 제목에 `[한국시리즈]` 처럼 시리즈가 붙어 정규시즌과 구별됨
- 경기가 없는 날·시간에는 외부 API를 아예 호출하지 않음
- Cloudflare Workers 무료 티어에서 동작. PC를 켜 둘 필요 없음

## 구조

```
Cron (1분마다)
  └─ 오늘 우리 팀 경기 계획 확인 (캐시 12시간 → 하루 1~2회만 조회)
       └─ 경기 없음 / 시간대 아님 → 즉시 종료 (외부 호출 0)
       └─ 감시 대상이 모두 끝난 지 30분 지남 → 즉시 종료
       └─ 배달 확인이 안 온 알림 재발송 (아래 "알림 배달 보장")
       └─ 감시 시간대 → 30초 간격으로 2회 폴링
            └─ 일정 API 조회 → 직전 스냅샷(D1)과 비교 → 상태 전이 감지
                 └─ 새 이벤트면 D1 기록 + 해당 알림을 켜 둔 구독자에게 Web Push
```

크론의 최소 간격은 1분이라 그대로 두면 알림이 최대 60초까지 밀립니다. 한 번 깨어난 김에
**30초 간격으로 두 번** 보도록 해 지연을 절반으로 줄였습니다. 대기는 CPU를 쓰지 않아
무료 티어 한도에 걸리지 않습니다.

| 파일 | 역할 |
|---|---|
| `src/index.js` | Worker 진입점. 크론 핸들러 + `/api/*` + 보안 헤더 |
| `src/kbo.js` | 네이버 KBO API 어댑터. 시리즈 판별, 순위·포스트시즌 판정 |
| `src/season.js` | 시즌·시간대 게이팅. 캐시로 불필요한 호출을 막음 |
| `src/detect.js` | 스냅샷 비교 → 알림 이벤트 생성 |
| `src/push.js` | Web Push 구현 (VAPID + aes128gcm, 외부 패키지 없음) |
| `src/security.js` | 입력 검증, SSRF 방어, 접근 제어 |
| `src/db.js` | D1 쿼리 |
| `public/` | PWA (토스 스타일 UI · 서비스워커 · 매니페스트 · 아이콘) |

### 데이터 출처

네이버 스포츠의 비공식 엔드포인트를 씁니다. 공식 문서가 없어 스키마가 예고 없이 바뀔 수
있으므로, 접점을 `src/kbo.js` 하나로 좁혀 뒀습니다.

| 용도 | 엔드포인트 |
|---|---|
| 경기 일정·점수 | `api-gw.sports.naver.com/schedule/games` |
| 순위·포스트시즌 기준 | `api-gw.sports.naver.com/statistics/categories/kbo/seasons/{year}/teams` |
| 전광판(이닝별 점수) | `api-gw.sports.naver.com/schedule/games/{gameId}/record` |
| 문자중계(종료 조기 감지) | `api-gw.sports.naver.com/schedule/games/{gameId}/relay` |

### 상태 전이 — 문서화되지 않은 `statusCode`

일정 API의 `statusCode`는 문서가 없어 **실측(`poll_log`)으로 값을 확인**했습니다.

| 값 | 의미 | 처리 |
|---|---|---|
| `BEFORE` | 경기 전 | 경기 전 |
| `READY` | 경기 전 (실제 시작보다 **최대 53분** 먼저 뜸) | **경기 전** — live로 보면 이른 시작 알림이 나감 |
| `STARTED` 등 | 진행 중 | 진행 중 |
| `ENDED` | 비공식 종료 (`RESULT` 로 확정되기 전 단계) | **종료** — 기다리면 종료 알림이 그만큼 밀림 |
| `RESULT` | 공식 종료 | 종료 |

원본 `statusCode`는 `poll_log`에 그대로 남겨, 모르는 값이 새로 나타나도 사후에 되짚을 수 있게 했습니다.

### 종료를 2분 앞당기기 — 문자중계

`ENDED` 조차 **실제 마지막 아웃보다 약 2분 늦게** 뜹니다. 2026-08-29 NC–한화전 문자중계의
`ptsPitchId`(초 단위 시각)로 확인했습니다 — 마지막 투구 21:22:09, `ENDED` 전이 21:24:17.

문자중계에는 그 아웃이 기록되는 즉시 종료 블록(`textOptions` 의 `type: 99` + `=====` 구분선)이
붙습니다. 잘못 보낸 종료 알림은 `dedup_key` 때문에 되돌릴 수 없어 **세 겹으로** 막았습니다.

1. **9회 이후 진행 중인 경기**에서만 호출 (응답이 이닝 하나 분량이라 매 폴링마다 부르면 부담)
2. `type: 99` **와** 구분선을 함께 확인 (타격 결과에 섞인 `===` 오인 방지)
3. 문자중계 점수와 일정 API 점수가 **다르면 쓰지 않음** (두 응답의 시점이 갈린 것)

이번 틱에 점수가 났으면 앞당기지 않고 다음 폴링에 맡깁니다. 끝내기 득점에서 `phase`를
미리 `result`로 바꾸면 득점 감지가 `live` 상태만 보므로 **끝내기 득점 알림이 통째로 사라집니다.**

실측(2026-09-01)으로 `ENDED` 대비 **54.5초** 앞당기는 것을 확인했습니다. 다만 문자중계의
종료 블록 자체도 실제 종료보다 3분쯤 늦게 붙어, 이보다 더 앞당기려면 다른 소스가 필요합니다.

### 시리즈 판별

네이버는 정규시즌/포스트시즌을 나타내는 **필드를 주지 않습니다.** 대신 포스트시즌 경기의
`gameId` 가 날짜 대신 고정 접두사로 시작합니다. 2023 · 2024 · 2025 세 시즌 데이터에서
아래 대응이 일치하는 것을 확인했습니다.

| gameId 접두 | 시리즈 |
|---|---|
| `20260823…` (경기일) | 정규시즌 **또는 시범경기** |
| `9999…` | 올스타전 (팀 코드도 `EA`/`WE`) |
| `6666…` | 순위결정전 |
| `4444…` | 와일드카드 결정전 |
| `3333…` | 준플레이오프 |
| `5555…` | 플레이오프 |
| `7777…` | 한국시리즈 |

문서화된 규칙이 아니므로, 모르는 접두사는 **정규시즌으로 간주**합니다.
알림이 아예 안 오는 것보다 시리즈 표기가 빠지는 편이 낫기 때문입니다.

### 이번 시즌 경기만 걸러내기

네이버의 `kbo` 카테고리에는 정규시즌·포스트시즌 외에 **시범경기와 올스타전, 지난 시즌 경기**가
섞여 있습니다. 그대로 쓰면 기록과 일정에 실제 경기가 아닌 항목이 잔뜩 들어옵니다.

| 섞여 있는 것 | 걸러내는 방법 |
|---|---|
| 지난 시즌 | `gameId` **끝 4자리 = 시즌 연도** (`20260822SSNC0`+`2026`). 11월 한국시리즈도 그해로 묶임 |
| 올스타전 | 접두 `9999` **및** 팀 코드 `EA`/`WE` — 양쪽으로 이중 확인 |
| 시범경기 | 개막일 이전 경기. 형식이 정규시즌과 **완전히 같아** 접두사로는 구분 불가 |

시범경기 판별이 까다로워 **개막일을 순위 API로 역산**합니다. 순위표의 `gameCount`는
정규시즌만 세므로, 완료 경기를 날짜순으로 늘어놓고 뒤에서 `gameCount`개를 세면
그 앞이 시범경기입니다. 2026 시즌 데이터로 10개 구단 전부 같은 날짜(**2026-03-28**)를
가리키는 것을 확인했습니다. 개막일은 매년 다르고 우천으로 밀릴 수도 있어 상수로 두지 않았습니다.

개막일을 못 구하면 시범경기 판별을 **포기**합니다 — 경기를 통째로 빠뜨리는 것보다 낫습니다.

### 응답 잘림 주의

`size` 파라미터는 kbo 경기가 아니라 **응답 전체**(퓨처스·국가대표 포함)에 걸리는 상한이고,
넘으면 아무 표시 없이 잘립니다. `size=2000`처럼 크게 주면 오히려 결과가 깨집니다(10건만 반환).
그래서 상한을 500으로 두고 **기간을 31일 단위로 쪼개** 여러 번 호출한 뒤 `gameId`로 중복을 제거합니다.
잘림이 감지되면 로그에 경고를 남깁니다.

### 포스트시즌 진출 판정

진출 기준(1위 한국시리즈 / 2위 PO / 3위 준PO / 4~5위 와일드카드)은 상수로 박지 않고
순위 API 응답의 `postSeason.teamColors` 값을 그대로 씁니다. KBO가 규칙을 바꿔도 따라갑니다.

순위 탭은 이 값으로 진출 구간을 나눠 표시합니다 — 구간 라벨("한국시리즈 진출",
"와일드카드 결정전 진출" 등)과 진출선 위치가 모두 API 응답에서 옵니다.

순위는 경기가 끝나야 바뀌므로 10분 캐시를 두되, **경기 종료를 감지하면 캐시를 즉시 비웁니다.**
크론이 종료 알림을 보내는 시점에 순위 캐시도 함께 무효화되어, 경기가 끝나면 바로 새 순위가 보입니다.

"**탈락 확정**"은 산술적으로만 판단합니다: 남은 경기를 전승해도 진출 하한선 팀의 *현재*
승수에 못 미치면 확정입니다. 하한선 팀의 승수는 줄어들 수 없으므로 이 판정은 뒤집히지 않습니다.
반대로 "가능"은 어디까지나 산술적 가능성이며 확률 예측이 아닙니다.

### 중복 발송 방지

모든 이벤트에 `dedup_key`(UNIQUE)를 둡니다. 크론이 중복 실행되거나 재시도돼도
`INSERT OR IGNORE` 가 걸려 같은 알림이 두 번 가지 않습니다.
득점은 키에 점수 조합을 넣어(`…:score:3-0`) 매 득점 상황이 각각 발송됩니다.

### 알림 배달 보장

**서버는 FCM이 받았다는 것까지만 알 수 있습니다.** 그 뒤 단말에 뜨기까지의 구간은
Worker 로그로 볼 수 없어, 실제로 알림이 안 뜬 사례가 여러 번 있었습니다 — 매번 이벤트 생성과
발송은 정상이었습니다.

그래서 **단말이 직접 알려오게** 했습니다.

```
서버: 알림 발송 (payload 에 events.id 포함)
  └─ sw.js: showNotification → POST /api/delivered  → events.delivered_at 기록
서버: 5분 지나도 확인이 없으면 → resent_at 표시 후 1회 재발송 (payload.resend)
  └─ sw.js: 알림함에 같은 tag 가 있나?
       ├─ 있음 → 조용히 넘기고 확인만 재전송 (이미 본 알림 — 두 번 울리지 않음)
       └─ 없음 → 정상 알림 (놓친 알림 — 여기서 살아남)
```

**서버가 단정하지 않는 것이 핵심입니다.** 확인 신호 자체가 실패할 때가 있어(화면에는 떴는데
확인만 안 올라온 사례) 서버 판단만 믿고 다시 띄우면 멀쩡히 본 알림이 두 번 울립니다.
최종 판단은 알림함을 직접 볼 수 있는 단말이 합니다.

| 값 | 의미 |
|---|---|
| 5분 | 재발송까지 기다리는 시간. 확인이 2분 53초 걸린 실측 사례가 있어 넉넉히 잡음 |
| 30분 | 이보다 오래되면 포기. 경기가 끝난 뒤 뜨는 알림은 혼란이 더 큼 |
| 1회 | 재발송은 이벤트당 한 번. 되풀이하면 확인이 영영 안 오는 구독 때문에 매 틱 반복됨 |

알림 `tag`는 **이벤트 id**(`nc-<id>`)입니다. 재발송이 와도 tag가 같아 알림함에서 정확히
매칭되고, 제자리 갱신될 뿐 두 번 뜨지 않습니다. 종류만으로 묶으면 그 범위가 경기를 넘어가
어제 경기의 종료 알림을 덮어써 **새 알림이 안 온 것처럼 보입니다.**

### 득점과 실점

알림은 둘 다 `score`로 나가고(구독 on/off는 `on_score` 하나), **기록 탭 라벨만** 갈립니다.
`events.kind`에는 실점이 `concede`로 저장됩니다 — 제목 문구를 뒤져 판단하지 않습니다.

발송 종류와 기록용 값이 달라지므로, 저장된 이벤트를 다시 보낼 때는 `dispatchKindOf`로
`concede → score`를 되돌립니다. 안 그러면 구독자 조회에서 걸러져 **실점만 조용히 재발송되지
않습니다.**

### 전광판 표시

야구 전광판은 **위가 원정(초), 아래가 홈(말)** 입니다. 홈/원정과 무관하게 우리 팀을 위에 두면
홈경기에서 두 줄이 뒤바뀌어 9회초와 9회말을 정반대로 읽게 됩니다. 우리 팀 강조는 위치가
아니라 `tr.mine` 클래스가 맡습니다.

치지 않은 이닝은 빈칸이 아니라 `-`입니다. 빈칸이면 "0점을 냈다"와 "치지 않았다"가 구분되지
않는데, 홈팀이 앞선 채 9회말을 치지 않는 경우는 흔합니다.

### 득점 이닝

득점 알림의 `· 5회말`은 **전광판에서 되짚습니다.** 폴링 순간의 `statusInfo`를 쓰면 이닝이
넘어간 직후에 걸릴 때 한 칸 밀린 이닝을 단언하게 됩니다.

총점은 일정 API, 이닝별 점수는 전광판 API에서 와 두 응답의 시점이 어긋날 수 있습니다.
**이닝별 합이 총점과 같을 때만** 이닝을 말하고, 아니면 생략합니다. 어긋났으면 2초 뒤 한 번
다시 불러봅니다 — 그 이벤트는 `dedup_key`로 묶여 있어 다음 틱에 다시 보낼 기회가 없기

## 설치

### 0. 사전 준비

- Node 18 이상
- Cloudflare 계정 (무료)
- Python 3 (아이콘을 다시 생성할 때만. 생성된 PNG는 저장소에 포함돼 있습니다)

```bash
npm install
npx wrangler login
```

### 1. D1 데이터베이스 생성

```bash
npx wrangler d1 create nc-alert
```

출력된 `database_id` 를 `wrangler.toml` 의 `REPLACE_WITH_YOUR_D1_DATABASE_ID` 자리에 넣습니다.

```bash
npm run db:init
```

### 2. VAPID 키 생성

```bash
npm run genkeys
```

- **공개키** → `wrangler.toml` 의 `VAPID_PUBLIC_KEY`
- **개인키** → 시크릿으로 등록 (파일에 넣지 마세요)

```bash
npx wrangler secret put VAPID_PRIVATE_KEY
```

`wrangler.toml` 의 `VAPID_SUBJECT` 를 본인 메일 주소로 바꿔 주세요.
푸시 서비스가 문제 발생 시 연락할 주소이며, 형식이 맞지 않으면 발송이 거부될 수 있습니다.

관리자 엔드포인트(`/api/admin/*`)를 쓸 계획이면 토큰도 등록합니다. 설정하지 않으면 잠긴 상태로 남습니다.

```bash
npx wrangler secret put ADMIN_TOKEN
```

### 3. 배포

```bash
npm run deploy
```

`https://nc-baseball-alert.<계정>.workers.dev` 주소가 나옵니다.

### 4. 휴대폰에 설치

**Android (Chrome)** — 주소를 열고 메뉴 → *홈 화면에 추가*. 앱을 열어 **알림 켜기**.

**iPhone (Safari)** — 반드시 **Safari**로 열어야 합니다.
공유 버튼 → *홈 화면에 추가* → **홈 화면 아이콘으로 다시 열기** → **알림 켜기**.
iOS는 홈 화면에 추가한 PWA에서만 푸시를 허용합니다.

설정 화면의 **테스트 알림 보내기** 로 동작을 확인하세요.

## 알려진 한계와 확인 필요 사항

운영하면서 실측으로 확인한 것들입니다. 원인이 밝혀진 것과 아직 아닌 것을 나눠 적습니다.

### 1. 배달 확인이 다음 푸시가 올 때까지 밀림 — **원인 확인됨**

2026-09-17 경기(3건)를 알림함 표시 시각과 함께 대조해 원인이 갈렸습니다.

| id | 감지 | 재발송 | 확인 | 확인 지연 | 알림함 표시 |
|---|---|---|---|---|---|
| 177 시작 | 18:31:26 | 18:36:59 | 18:56:38 | **25분 11초** | 6:31 (감지 시각) |
| 178 득점 | 18:56:34 | 19:02:33 | 19:28:37 | **32분 03초** | 7:02 (재발송 시각) |
| 179 실점 | 19:28:34 | 19:33:59 | 19:34:01 | **5분 27초** | 7:33 (재발송 시각) |

**확인은 항상 "다음 푸시가 나간 2~3초 뒤"에 도착합니다.**

```
177번 확인 = 178번 푸시 +3초
178번 확인 = 179번 푸시 +3초
179번 확인 = 179번 재발송 +2초
```

즉 문제는 알림 표시가 아니라 **`/api/delivered` 의 `fetch` 가 서비스워커가 잠들면서 보류되고,
다음 푸시가 워커를 깨울 때 비로소 나간다**는 것입니다. 177번이 그 증거입니다 — 알림함에
감지 시각(6:31)으로 떠 있으니 첫 푸시는 제대로 표시됐는데, 확인만 25분 뒤에 왔습니다.

**따라서 `reportDelivered()` 를 `showNotification()` 앞으로 옮기는 것으로는 해결되지 않습니다.**
핸들러 안의 순서 문제가 아니라 나가는 요청 자체가 보류되기 때문입니다. 확인 지연이
25~32분이라 `RESEND_AFTER_MS` 를 늘려 피하는 것도 불가능합니다(포기 기준이 30분).

**현재 결론:** 확인 신호는 신뢰할 수 없고, 헛된 재발송은 감수합니다. 대신 `sw.js` 의
tag 검사가 중복 표시를 막아 주므로(177번이 실제로 그렇게 걸러졌습니다) 사용자에게는 해가
없습니다. 재발송 2건(178·179)은 첫 푸시가 정말로 안 떠서 **알림을 살려냈습니다.**

이 조사 과정에서 실제 결함이 하나 드러나 고쳤습니다 — 재발송 알림이 원래 감지 시각이 아니라
재발송 시각으로 찍혀, 1분 만에 감지한 알림이 6분 늦은 것처럼 보였습니다(아래 2번과 혼동됨).

### 2. 알림이 경쟁 앱보다 1분 늦음 — **원인 확인됨, 대안 불확실**

네이버 일정 API의 상태 전환 자체가 늦습니다. 2026-09-16 실측:

```
09:30:39  READY    경기전
09:31:11  STARTED  1회초    ← 네이버가 여기서 바꿈
```

우리는 네이버가 바꾼 **직후 즉시** 감지했습니다(폴링 간격 32초, 정상). 같은 경기에서 경쟁
앱은 09:30에 알렸습니다 — **네이버 API가 바뀌기 30초 이상 전**입니다.

종료는 문자중계로 54.5초 앞당겼지만(위 참고), 문자중계의 종료 블록도 실제보다 3분쯤 늦습니다.
시작·득점까지 문자중계로 옮기면 나아질 수 있으나, **응답 크기를 아직 측정하지 못했습니다.**
매 폴링마다 부르려면 그 값이 먼저 필요합니다.

### 3. 득점 이닝·홈런 표시가 가끔 빠짐 — **원인 확인됨, 의도된 동작**

전광판 API가 그 시점에 이닝별 점수나 홈런 기록(`etcRecords`)을 아직 안 실어준 경우입니다.
2초 뒤 한 번 다시 부르지만 그래도 못 잡는 경우가 있습니다.

**틀린 이닝을 단언하느니 생략하는 쪽**을 택했으므로 이 자체는 의도된 동작입니다. 다만 빈도를
줄이려면 문자중계를 쓰는 것이 근본적입니다(2번과 같은 과제).

### 4. 알림함에서 알림이 사라지는 것은 앱 밖의 일

배달 확인이 정상인데도 알림함에 없는 경우가 있었습니다(2026-09-12, 5건). `delivered_at` 이
채워졌다는 것은 **단말이 알림을 띄우고 서버에 확인까지 보냈다**는 뜻이므로, 그 뒤 사라진 것은
사용자가 지웠거나 Android가 정리한 것입니다. 앱에서 손댈 수 있는 부분이 아닙니다.

### 운영 중 확인용 쿼리

```sql
-- 알림별 생성 · 배달 · 재발송 시각
SELECT id, kind, title, body, created_at, delivered_at, resent_at
FROM events WHERE game_date = 'YYYY-MM-DD' ORDER BY id;

-- 점수가 실제로 어떻게 움직였는지 (폴링 끊김도 함께 드러남)
SELECT MIN(created_at) AS first_seen, status_info, home_score, away_score
FROM poll_log WHERE game_id LIKE 'YYYYMMDD%'
GROUP BY home_score, away_score ORDER BY first_seen;
```

`resent_at` 이 전부 비어 있으면 정상입니다 — 재발송이 필요 없었다는 뜻입니다.

### 폰트

명세가 지정한 Copernicus·StyreneB는 Anthropic 라이선스 폰트라 공개 웹폰트가 없습니다.
DESIGN.md가 직접 명시한 대체재를 씁니다 — 세리프는 **Cormorant Garamond**, 산세리프는 **Inter**.

다만 이 앱은 한글이고 두 폰트 모두 한글 글리프가 없습니다. 폰트 폴백 체인으로 해결합니다:
라틴 문자와 숫자는 대체재가, 한글은 **Noto Serif KR**(제목) / **Pretendard**(본문)가 렌더링합니다.
점수와 순위 숫자가 세리프로 나오는 것은 의도된 것으로, 명세에서 가격을 세리프로 쓰는 것과 같은 원리입니다.

### 아이콘 — Tossface

타임라인의 아이콘(⚾ 시작 · 🔥 득점 · 🌧️ 취소 · 🏁 종료 · 🏆 포스트시즌)은
[Tossface](https://github.com/toss/tossface)입니다.

Tossface는 **이모지 전용 서체로 한글 글리프가 없습니다.** 본문 한글 서체로는 쓸 수 없어
아이콘 용도로만 사용합니다. 폰트 전체는 12MB, 필요한 서브셋만 골라도 약 4MB라
같은 저작물의 **SVG 판을 `<symbol>`로 인라인**했습니다 — 아이콘 5개에 약 7KB입니다.
외부 CDN 의존이 없어 CSP도 그대로 유지됩니다.

```bash
npm run gentossface -- <tossface 저장소 경로>
```

### 한국어 조사 — es-hangul

알림 문구와 순위 설명의 조사 처리에 [es-hangul](https://github.com/toss/es-hangul)을 씁니다.

```
삼성과의 홈 경기가 시작됐어요        롯데와의 홈 경기가 시작됐어요
두산을 넘어야 진출권에 들어요         KT와의 홈 경기가 시작됐어요
```

영문 약어를 한글 발음으로 읽어 조사를 고르기 때문에(`KT` → `케이티` → `와`,
`SSG` → `에스에스지` → `와`) KBO 팀명을 예외 처리할 필요가 없습니다.
한국어 문법 처리는 전부 서버(Worker)에 모아 두었고, 앱은 완성된 문장을 그대로 표시합니다.
